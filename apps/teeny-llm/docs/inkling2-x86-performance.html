Inkling-2-Mini on x86, natively, with an eye on the Intel NPU

An x86-64 backend for teenyc and teenygrad runs Inkling-2-Mini natively on an Intel Core Ultra laptop. It matches the transformers reference token for token and decodes about 3× faster than the SpacemiT K3. The NPU helps prompts at most, not decode.

Decode is about 3× the K3 and prompts about 3×. A token reads about 3.6 GB of weights, and this machine reads 101 GB/s, so the floor is about 36 ms (about 28 tok/s). 15–20 tok/s looks reachable.

The machine

  • CPU: Intel Core Ultra X9 388H (Panther Lake), 16 cores (P, E and low-power E).
    • Has AVX2, FMA, F16C, GFNI and AVX-VNNI.
    • No AVX-512, no AMX, and no VNNI-INT8.
  • Memory: 64 GB LPDDR5X-8533. Measured read bandwidth: 28 GB/s on one thread, 83 GB/s on four, 101 GB/s on all 16.
  • NPU: Intel AI Boost, NPU 5 (architecture 5010), driver 32.0.100.5600, OpenVINO 2026.4.1. 25 TFLOPS FP16 and 50 TOPS INT8; no BF16, FP8 or FP4.
  • OS: Windows 11. teenygrad and teenyc run in WSL2 (Ubuntu 26.04, 54 GB of memory). The NPU is reachable only from Windows.

Correctness

Generating step by step, the transformers reference (scripts/inkling2-ref-model.py) took hours per prompt. So the check is teacher-forced: one forward pass over the prompt plus teenygrad's 32 generated tokens. At every position, the reference's most likely token has to be the one teenygrad generated.

1. An x86 backend

teenyc. The existing abstract TritonCPU backend (CpuBackend) already chooses x86 vector lowerings from the feature set, and RiscvBackend is one subclass of it. X86Backend is a second:

  • It emits an ELF object for the requested LLVM cpu and links it with ld.lld -m elf_x86_64.
  • The cpu is x86-64-v3 by default, or native, which resolves to the host.
  • A new target, x86_64-teeny-kernel, routes to the mlir backend as riscv64-generic does, so ordinary x86 builds are untouched.

teenygrad.

  • drivers/teeny-x86 is teeny-riscv's host code with the lp64d launcher replaced by a System V x86-64 one:
    • six integer registers;
    • eight SSE registers, with no NaN-boxing;
    • floats past xmm7 go on the stack.
    A unit test makes a real call through the launcher with arguments spilling to the stack.
  • An x86 feature runs from teeny-runtime up to teeny-bench, so the model builds with --features inkling2,x86.

2. tt.gather → vpshufb

  • The problem: the NVFP4 experts' 16-entry table lookup had no x86 lowering. LLVM turned it into a lane-by-lane loop of address extracts and byte inserts, and perf put 45% of the time in that kernel.
  • The fix: a table of at most 16 bytes now becomes vpshufb, and one of at most 8 dwords becomes vpermd/vpermps.
  • The result: decode went from 1.2 to 6.4–7.0 tok/s, with output unchanged.

3. int8 dot → VNNI

A new teenyc pass, ConvertDotToVNNI, lowers an i8 × i8 → i32 tt.dot to vpdpbusd:

  • Layout: columns are lanes. Four k values of each column pack into one 32-bit lane, and each row's four bytes are broadcast.
  • Exactness: B goes in as B XOR 0x80, and 128 × Σ A[m, :] is subtracted once per row.
  • No-shuffle cases: a transpose of a row-major tile, or a reshape of a [0, 2, 1] transpose, becomes a plain bitcast.
  • Tests: exact against a host reference, including i8 extremes, in drivers/teeny-x86/tests/test_int8_dot_x86.rs.

The NVFP4 expert kernel (expert_gemv_nvfp4_vnni_forward) makes each 16-element block one K = 16 int8 dot:

  • Weights are stored as [2][rows][4] bytes per block: low nibbles hold elements {0–3, 8–11}, high nibbles {4–7, 12–15}. So b & 15 and b >> 4 are already packed, with no interleaving.
  • vnni_interleave builds this layout from the format-2 bytes at load time. The converted checkpoint is unchanged, and the K3 build reads exactly what it did.
  • It's the x86 default; INKLING2_VNNI_EXPERTS=0 switches back to the old kernel.

The first version was not faster. A cycle breakdown of the kernel showed why:

  • 33% register spills to the stack;
  • 30% scalar activation loads;
  • 18% repeated broadcasts;
  • about 5% the actual dot and table lookups.

Fixing those three (contiguous activations, one dot per block, broadcasts hoisted) brought prompts to 13.7 tok/s.

4. E4M3 block scales in one shift

Decoding the block scales was then 17% of the kernel. An E4M3 byte's low seven bits, shifted to bit 20, form an f32 exactly 2⁻¹²⁰ times its value, subnormals included:

ws = bitcast_f32((b & 0x7F) << 20) * (2^120 * es)

Powers of two multiply exactly, so every scale is bit-identical to before. It takes 4 instructions per 8 scales instead of about 9.

5. Launch overhead, FMA and signed int8 weights

Each change was measured interleaved against the build before it, over three rounds, and each left both replies byte for byte identical.

  • The spin pool handed each job over through a mutex that all 7 workers locked at once, on each of about 2,470 launches per token. The job pointer is now two atomics, ordered by the epoch. Decode p50 went from 127–131 to 107–116 ms (−14%).
  • FMA: X86Backend fuses each multiply-add into one vfmadd, which rounds once instead of twice. Prompts +6%, decode p50 −3.5%.
  • Signed int8 weights: the int8 linears stored each weight as q + 128 and subtracted 128 after widening, a quarter of the inner loop. On x86 the loader flips the bytes to q and the kernel sign-extends. The arithmetic is identical. Prompts +19%, decode p50 about −7%, load time unchanged.
  • No clear gain: thread count (6–10) and spin time (50–1000 µs).
  • The laptop's "AI Engine" power profile is 25–35% slower (decode p50 146–162 ms against 111–123 ms). It favours the NPU, and teenygrad runs on the CPU. Use Performance or Balanced.

6. Opt-in: VNNI int8 linears

The int8 linears top out near 70 GB/s while the experts reach about 100, because the inner loop spends a shuffle widening each 8 weights. INKLING2_VNNI_LINEARS=1 quantises a linear's input per 16-element block, as the experts' is, and runs each block as an int8 dot lowered to vpdpbusd.

  • Prompts about +15%, decode p50 about −7%.
  • Off by default. Over two 100-token replies the reference's argmax matched at 194 of 200 teacher-forced positions with it, against 196 without. Every miss in both builds is a near-tie: the top two are within about 0.2 in logit.
  • No clear gain: running tiny grids on the calling thread, and borrowing the per-launch kernel lookup's keys instead of allocating them.

Threads. On Panther Lake's mix of P, E and low-power cores, every launch waits for its slowest thread:

  • decode is best at TEENY_X86_THREADS=8;
  • prompts are best at 8–14;
  • 16 threads is slower even on an idle machine.

WSL can't pin threads to physical cores, and decode varies by about ±10% from run to run.

  • Experts can't go to the NPU. At 6–8 ms per layer, the 48 layer executions per token would cost about 300 ms. The NPU also has no NVFP4 or FP8, so it would mean re-quantising the experts.
  • Decode should stay on the CPU. Each NPU call has a fixed cost of about 0.4 ms. With about 100 calls per token, offloading the dense layers would cost about 40 ms where the CPU now spends about 22.
  • Prompts could gain at most about 20%. The NPU is 2–3.5× faster at 16 tokens per call, but the layers it can take are only 21% of prompt time. The experts are 63%. It also needs a Windows-side process. not built

What's left

  • The VNNI expert kernel still spills registers. There are 94 stack references in its assembly.
  • The int8 attention linears (about 35 ms of a decode token) convert every weight to f32. Using VNNI there would need int8 activations, which changes the arithmetic, so it needs a quality check first.
  • The MXFP8 experts (layers 20–23) have no x86 tuning yet.
  • Small ops and launch gaps add up to about 50 ms per token. The K3 document's SGLang/vLLM fusion list applies here too.
  • No x86 SLEEF: math calls go to libm, though no hot kernel calls them.

Found along the way

  • teenyc mis-shapes tt.cat of two 3-D tensors. Two [2, 32, 4] tensors come out as [4, 8, 64]. The kernel concatenates flat instead.
  • T::dot with no accumulator accumulates in its input type (i8). The kernel passes an explicit i32 zero.
  • Pre-existing: 7 of 8 tests in test_inkling2_model.rs fail on any backend, before any kernel runs. They supply f32 weights under names the graph now gives *.weight_bf16 slots, and their stand-in width of 24 isn't a multiple of 16.
  • Pre-existing: teeny-riscv and teeny-x86 don't build on their own. teeny-core/src/model/mod.rs:162 uses std::path without the std feature.

Building and running

The compiler (realitymatrix/teeny, branch feat/x86-cpu-backend, based on feat/rvv-tt-gather) needs a few things the README doesn't mention.

A local bootstrap.toml with these settings:

  • llvm.download-ci-llvm = false, because CI LLVM has no MLIR or LLD;
  • rust.codegen-backends = ["llvm", "mlir"], which is what adds MLIR to the LLVM build;
  • rust.lld = true;
  • rust.deny-warnings = false, because of an unused variable in rustc_llvm/build.rs.

Also:

  • the fork's own submodules initialised by hand: melior, mlir-sys, tblgen-rs, triton, sleef and llvm-project. They use git@ URLs, so url.https://github.com/.insteadOf is needed without an SSH key.
  • clang-22, which rustc_llvm/build.rs hard-codes for Triton's NVIDIA backend.
  • nanobind on CMAKE_PREFIX_PATH, for Triton's Python module.
./x.py build --stage 1 -j 4 --warnings warn    # about 1.5 h here
export TEENYC_PATH=<teeny>/build/host/stage1/bin/teenyc TEENYC_CAPABILITY=native
cargo build --release -p teeny-llm --no-default-features --features inkling2,x86 \
  --example inkling2 --example inkling2_convert
cargo build --release -p teeny-bench --no-default-features --features inkling2,x86
